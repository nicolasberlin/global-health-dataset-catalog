# Investigating a search

Use this optional maintainer guide to explain a search result with reproducible
evidence. It is not required to run the API. The templates are blank forms,
separate from the JSON report generated by the [API client](README.md).

The interface's **Export diagnostic trace** action exports persisted search
state and collection attempts. It is a partial export, not a completed manual
investigation. Leave missing facts as `null` or `unknown` and record which
evidence is unavailable.

## Prepare an investigation

1. Copy [search-trace.json](templates/search-trace.json) into a private directory
   for the search. Set `is_template` to `false` and record the real export date.
2. Fill in the context, available evidence, stages and findings.
3. Copy [search-report.md](templates/search-report.md) into that directory and
   write the report using evidence IDs from the trace.
4. Preserve the original observations when retrying or correcting behavior.
   Record each reproduction as a separate operation and compare its results.

The trace records observations; the report explains what they support. A current
reproduction alone does not establish what happened during an earlier execution.

## Available evidence

| Source | Information | Limits |
| --- | --- | --- |
| `GET /collector/searches/{id}/progress` | Current state, candidates, decisions, jobs, counts and saved dataset IDs | A snapshot, not an event history |
| `GET /collector/searches/{id}/diagnostics` | Owner-scoped aggregate of search, collection and classification observations | Partial first pages, no raw pages or cookies |
| `GET /collector/collection-jobs/{id}/diagnostics` | Methods, resource checks, coverage and first model-history page | Default 100 methods, maximum 200; up to 100 checks per method and 2,000 per page, with `checks_truncated` |
| `GET /collector/collection-jobs/{id}/classification-history` | Owner-scoped model-call history | Paginated, with bounded offsets |
| `GET /collector/repository-candidates/{id}/classification-history` | Owner-scoped repository-classification calls | Paginated, with bounded offsets |
| `GET /collector/searches/latest` | Latest search belonging to the caller | Changes after a new search; retain the original `search_id` |
| Operational server logs | Correlation IDs, events and durations | Depend on retention; do not reconstruct every discarded link |
| Authorized database inspection | Persisted states, votes and jobs | Unrecorded causes remain unknown |
| Browser network panel | Client polling, HTTP status and interruptions | Does not show the server collector's outgoing requests |
| Controlled reproduction | Current behavior on a specified input | New evidence, not a historical record |

History pages default to 100 entries, accept `limit` from 1 to 200 and `offset`
from 0 to 10,000. Follow `next_offset`; `history_truncated` indicates remaining
entries. Method history and model history have independent pages. A bounded
search export can therefore be incomplete even when its HTTP request succeeds.

Each classification call records its run, voter/model, attempt, retry cycle,
start/end time, outcome and diagnostics. Later success retains earlier failures;
restart interruptions are recorded too. The interface shows this under **Model
classification history**, and job responses expose `classification_history.attempts`.
Search exports include `repository_classifications`.

The API selects safe history fields and exposes controlled `errors` diagnostics,
not raw technical `error` text. Stored entries are filtered again on read. Imported
snapshots can use `evidence: legacy_snapshot` with `started_at: null`; they cannot
restore overwritten failures. New observations use `evidence: live`. Raw invalid
model responses, API keys and exception details are not public evidence.

See the [HTTP contract](../docs/api-integration.md#diagnostic-history),
[pipeline outcomes](../docs/reference/pipeline-outcomes.md),
[frontend tracking](../docs/ONBOARDING.md#optional-frontend) and
[operational logs](../docs/DEPLOYMENT.md#internal-operational-logs).
Read state with GET requests; a new search or retry POST schedules new work.

## Trace conventions

- Use ISO 8601 timestamps with a timezone, preferably UTC. The report can display
  `Europe/Zurich`; API timestamps and browser-local display are different views.
  Record durations in milliseconds.
- Use `null` for unknown values; zero means a measured zero.
- Empty arrays contain no recorded entries. State their coverage in
  `export.coverage` and list gaps in `export.missing_evidence`.
- Keep `summary.execution_status` and `summary.outcome` equal to observed API
  values. Manual stage statuses do not change the API contract.
- Stage statuses are `not_run`, `running`, `succeeded`, `empty`, `rejected`,
  `failed` or `unknown`. Include a reason and `evidence_refs` where available.
  Missing logs do not prove `not_run`; `empty` requires evidence of completion.
- `tracking` describes client reads. Stopped polling does not prove that server
  processing stopped or failed.
- Record the frontend/backend revisions actually executed. A local commit does
  not establish the deployed revision.

The supplied JSON is a template, not a JSON Schema or an API response contract.
Use these fields when populating its arrays:

| Array | Suggested fields per entry |
| --- | --- |
| `context.models` | `voter_id`, `model_id`, `model_version`, `parameters` |
| `context.expected_results` | `reference_url`, `doi`, `expected_decision`, `reason` |
| `sources` | `source_id`, `provider`, `request_query`, `filters`, `limit`, `status`, `http_status`, `result_count`, `excluded_count`, `exclusion_reasons`, `duration_ms`, `errors`, `evidence_refs` |
| `candidates` | `candidate_id`, `source_id`, `title`, `url`, `doi`, `classification_status`, `votes`, `collection`, `files`, `evidence_refs` |
| `candidates[].votes` | `stage`, `voter_id`, `model_id`, `attempt`, `decision`, `relevance`, `reason`, `duration_ms`, `error_code`, `evidence_refs` |
| `candidates[].collection` | `job_id`, `status`, `outcome`, `requested_url`, `final_url`, `http_status`, `content_type`, `discovery_method`, `extracted_link_count`, `excluded_links`, `reason`, `evidence_refs` |
| `candidates[].files` | `file_id`, `url`, `declared_format`, `detected_format`, `download_status`, `http_status`, `bytes_examined`, `validation_status`, `checks`, `reason_code`, `reason`, `dataset_id`, `persistence_status`, `evidence_refs` |
| `events` | `event_id`, `timestamp`, `stage`, `operation`, `search_id`, `candidate_id`, `job_id`, `file_id`, `attempt`, `status`, `duration_ms`, `error_code`, `evidence_refs` |
| `evidence` | `evidence_id`, `kind`, `captured_at`, `artifact_path`, `locator`, `description`, `redacted` |
| `findings` | `finding_id`, `observation`, `proposed_cause`, `confidence`, `evidence_refs`, `missing_verification` |
| `proposed_actions` | `action_id`, `finding_ids`, `priority`, `change`, `expected_result`, `acceptance_test`, `status` |

`confidence` is `confirmed`, `hypothesis` or `undetermined`. A model's returned
justification is evidence of its response, not a reconstruction of its internal
reasoning. Put observed limits/timeouts and their source in `context.parameters`;
do not assume current defaults describe an older execution.

## Questions the report should answer

- Did discovery query the intended sources with the intended filters? Did a
  candidate limit prevent a conclusion about the full result set?
- Did classification match the need? Distinguish a model error from a valid
  rejection, and identify individual calls and attempts.
- How far did accepted candidates get? No extracted link, excluded link, denied
  access, timeout, unknown format, invalid file and failed persistence differ.
- Were results saved and retrievable by the client?
- Which causes are confirmed, which remain hypotheses, and what check would
  distinguish them?

Measure precision or recall only against an annotated reference set. Positive
vote counts and saved-file rates alone do not measure scientific quality.

## Retention and sharing

Retain useful correlation IDs and minimal evidence excerpts. Exclude API keys,
cookies, authentication headers, signed URLs and raw medical content. Queries
can themselves contain private information. The blank templates are versioned;
review each completed trace before sharing it. More specific technical causes
can require internal evidence available only to an authorized operator.
