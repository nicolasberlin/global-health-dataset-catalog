# Optional search laboratory

This is a removable local tool, separate from the product. It reads existing
owner-scoped searches, groups methods by actual worker execution, preserves
candidate snapshots and compares evidence. Opening it never launches a collection.
This optional tool keeps its code, documentation, test cases and private data
together in **search_lab/**. It has its own startup commands and consumes
diagnostics from the main API; the main API never depends on the laboratory.
Running or testing the normal API does not require starting this tool or
installing its frontend dependencies. API client reports remain in
[`research/api/`](../research/README.md).

## Start the optional laboratory

Use this only when you want to investigate existing searches. The target API and
its PostgreSQL database must already be running and reachable from this computer.
The lab starts separately and reads those targets; it does not start the main API.

From the project root, create the lab's own private configuration once:

```sh
cp search_lab/example.env search_lab/.env
```

Edit **search_lab/.env**:

- Set `LAB_DATABASE_URL` to the target API's PostgreSQL database, preferably using
  a SELECT-only database role.
- Set `LAB_API_BASE_URL` to that same API's local address (port 8001 by default).
- Use `API_AUTH_MODE=local` with a local target API. Both use `local-user`.
  The laboratory has no login or access token; public visitor mode is unsupported.

Keep credentials in the private `.env`, not in `example.env`. The startup script
loads this lab configuration; it does not require the project's `.env.local`.
The main API does not read the lab's configuration.

Use Node.js 22.12 or later within 22.x for the lab interface, matching the major
version used in CI. Other accepted versions are declared in
[`frontend/package.json`](frontend/package.json).
Use the same Python setup as the main project; see
[requirements and uv installation](../docs/ONBOARDING.md#requirements-and-dependencies).
From the repository root, install the locked development dependencies into
`.venv`, then install and start the separate lab interface:

```sh
uv sync --locked --extra dev
npm --prefix search_lab/frontend ci
sh search_lab/start.sh
```

Open **http://127.0.0.1:5174**. The separate lab API listens on **127.0.0.1:8003**.
The laboratory uses local loopback access and has no login or access token.
The tool is restricted to loopback clients and laboratory origins.

1. Filter **Search history** to **External repositories** and select a search.
2. Choose a candidate and inspect its dated method attempts.
3. Fill the research notes, keeping expectations and hypotheses separate from facts.
4. **Save this candidate** saves only the selected candidate, its title, URL, classification and collection traces, without overwriting old evidence.
5. After a new normal application attempt, refresh and capture another snapshot.
6. Compare two snapshots of the same candidate URL. The selectors list only snapshots for the currently selected candidate. Older whole-search snapshots remain downloadable but are excluded from comparison.

## Isolation and evidence

The capture endpoint accepts `SnapshotCaptureRequest`: a candidate ID and research
notes. It records existing evidence without scheduling collection work.

The lab's separate PostgreSQL pool enforces read-only sessions and transactions.
It starts no workers, applies no migrations and never marks jobs interrupted.
Use a SELECT-only database role for additional isolation. `LAB_DATABASE_URL` and
`LAB_API_BASE_URL` must refer to the same application instance.

Private evidence defaults to **search_lab/data/evidence/**, inside this tool,
under a hashed owner directory. `LAB_EVIDENCE_DIR` can select another private
directory. Screenshots belong in **search_lab/data/captures/**; they are added
manually, not generated by the API client. See the [lab file guide](data/README.md)
for the directory contents. Each new snapshot contains one candidate, capture time, Search ID, job IDs, available
attempt IDs, notes and a checksum. The checksum detects accidental changes;
it is not a trusted digital signature. Saving does not trigger a download. Optional manual downloads are additional copies.

Job results are **current at capture time**, not necessarily their original state.
Historical method traces are dated observations. Worker claim timestamps separate
attempts even within one retry cycle. Previous-case links concern available history
only. Unknown collector versions, historic save counts and missing durations remain
unknown. API diagnostics and claim lookups are two reads, not one atomic DB snapshot.

## Targeted reproductions

Scenarios use the real collector's registry, connectors, network restrictions and
browser. They never persist datasets to PostgreSQL. Live operations require
`--live`; model calls additionally require `--include-ai`. Raw HTML, provider
JSON bodies, cookies and full data files are not saved. A code fingerprint and
scenario duration are recorded; code changes during execution make the version unknown.

The command-line scenarios are separate from `start.sh`. In their terminal,
load any required lab settings explicitly:

```sh
set -a
source search_lab/.env
set +a
```

```sh
PYTHONPATH=backend:. .venv/bin/python -m search_lab.scenarios.run api \
  'https://dataverse.harvard.edu/file.xhtml?fileId=123' \
  --offline-json search_lab/cases/dataverse-file/metadata.json

PYTHONPATH=backend:. .venv/bin/python -m search_lab.scenarios.run api \
  'https://dataverse.harvard.edu/file.xhtml?persistentId=doi%3A10.7910%2FDVN%2FAXRYQD%2FRTPFQI' --live
```

Use `html` or `browser` instead of `api` for those observations. Browser mode
requires the existing isolated service/proxy and private browser environment.
`collection --live --include-ai` also runs classification and bounded resource
checks, but does not save a catalog record. Individual-stage successes are not
proof of complete search success. Reproductions write JSON under
**search_lab/data/evidence/reproductions/** by default (`LAB_EVIDENCE_DIR` overrides
the evidence root).

## Optional fresh-database experiments

This advanced mode needs a source `DATABASE_URL` with permission to create a
separate database; it is distinct from the lab's recommended read-only
`LAB_DATABASE_URL`. Set it explicitly in the experiment terminal and load the
RCP settings required for a full search. These commands do not automatically
load the main API's configuration files. In that terminal:

```sh
PYTHONPATH=backend:. .venv/bin/python -m search_lab.scenarios.experiment init
PYTHONPATH=backend:. .venv/bin/python -m search_lab.scenarios.experiment start
```

This creates **ghdc_lab_experiments** and starts the normal API on port **8011**
against it. No existing DB is reset or dropped. In another terminal:

```sh
PYTHONPATH=backend:. .venv/bin/python -m search_lab.scenarios.experiment search \
  --query HIV --include-ai
```

It uses the full normal search pipeline and saves its export in
**search_lab/data/evidence/experiments/** by default (`LAB_EVIDENCE_DIR` overrides
the evidence root). Tracking stops after ten minutes; unfinished
server work is not implicitly cancelled. Port 8011 must be the dedicated API you
started above. Repeated searches can reuse experimental catalog results. Choose
a new `--name ghdc_lab_...` for a fresh campaign.

To view the experiment history, restart the lab with `LAB_DATABASE_URL` targeting
that DB and `LAB_API_BASE_URL=http://127.0.0.1:8011`.

## Test and remove

```sh
PYTHONPATH=backend:. .venv/bin/python -m pytest search_lab/tests
npm --prefix search_lab/frontend test
npm --prefix search_lab/frontend run build
```

Stop the laboratory and optional experimental API. If you want to retain private
observations, copy **search_lab/data/** outside the tool before removing
**search_lab/**; deleting the tool also deletes its local data. Preserve
any custom `LAB_EVIDENCE_DIR` separately. Production routes, UI, dependencies and
schema have no lab-specific integration to revert. Experimental databases remain
until you explicitly delete them.
